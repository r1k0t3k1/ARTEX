# サイド質問の長い会話とコンテキスト予算

2026-09-11 修正。当初の実装はリクエスト JSON の文字数をそのまま token とみなし、メインタスクの 32K 出力予約を継承していたため、HTML、JS、ツール結果が多いと正常なサイド質問でも早期に拒否されていました。

## オープンソース実装の確認

- [Grok CLI のサイドコンテキスト](https://github.com/superagent-ai/grok-cli/blob/fb97af83f06dca873281d60168430f06c8de6324/src/agent/agent.ts#L739)：直近のユーザー、アシスタントのテキストから断片を抜き出し、文字予算は約 2000、各条は最大 400 文字に切り詰める。この経路では連続したサイド質問応答の履歴を維持しない。
- [Grok CLI の独立リクエスト](https://github.com/superagent-ai/grok-cli/blob/fb97af83f06dca873281d60168430f06c8de6324/src/utils/side-question.ts)：独立したキャンセルシグナル。モデルが対応していれば出力上限は 2048 tokens。ツールは提供しない。
- [Grok CLI のメインセッション圧縮](https://github.com/superagent-ai/grok-cli/blob/fb97af83f06dca873281d60168430f06c8de6324/src/agent/compaction.ts)：token を推定し、直近の内容を保持し、新しい内容を旧要約に更新し、ターンをまたぐ切り詰めを処理する。
- [OpenCode のセッション圧縮](https://github.com/anomalyco/opencode/blob/b3f1a96c6dd7adeb28b36dd11add1998fc84d67b/packages/core/src/session/compaction.ts)：完全なリクエストの推定、出力/バッファの予約、直近の内容とローリング要約、ツールなしの要約リクエスト。この実装は既定で直近予算 8000、要約出力上限 4096 tokens。
- [OpenCode のオーバーフロー復旧](https://github.com/anomalyco/opencode/blob/b3f1a96c6dd7adeb28b36dd11add1998fc84d67b/packages/core/src/session/runner/llm.ts)：アシスタントの出力がまだ始まっていない場合にのみオーバーフロー復旧を試み、復旧後の呼び出しは同じオーバーフロー復旧経路に入らない。

ARTEX は独立した出力予算、直近の内容とローリング要約、限定的な復旧という手法を取り入れています。norma v0.3.6 の構造化メッセージとツールのペアリングを維持し、Grok のテキスト抜き出しをそのまま踏襲してはいません。OpenCode のメインセッション圧縮イベントを ARTEX のメイン transcript に書き込むこともしていません。

## リクエスト予算と実行

- メッセージは norma のコンテンツブロック単位の UTF-8 バイト推定と 4/3 の余裕を踏襲し、さらにシステムプロンプト、ツール schema、メッセージラッピングのオーバーヘッドを加算する。推定はモデルの正確な token 数ではない。
- サイド質問の出力は既定で最大 8192 tokens で、メイン設定で既に指定された出力上限も超えない。サービスの環境変数 `ARTEX_BTW_MAX_OUTPUT_TOKENS` で 256〜32768 の上限を設定できる。製品の既定モデルやメインタスクのパラメータは変更しない。
- 入力予算はコンテキストウィンドウから出力上限と安全余裕を引いたもの。ウィンドウが不明な場合はプラットフォーム既定の 200K を使う。安全余裕はウィンドウの 5% で、最小 128、最大 8192 tokens。
- 成功した質問応答はインクリメントするシーケンス番号ごとに 1 バッチ最大 20 組を読み込む。原文は最大 20 組を保持し、その token 予算は入力予算の 1/4 以内かつ 16K 以下。
- 予算を超えた質問応答はローリング要約に更新する。要約には履歴の出所とコンテキスト時刻が付く。過去のアシスタント回答は新しいツール証拠と同一ではなく、衝突時は最新のメインスナップショットを優先する。
- メインコンテキストがまだ長すぎる場合は、コピー内の古いメッセージのみを要約し、直近は最大 8K tokens を保持する。切り詰め位置がツール呼び出しと結果を分割することはない。大きすぎる単一組は丸ごと要約に入る。
- 要約入力は実際の残りウィンドウに応じて UTF-8 安全に分割し、出力上限は 2048 tokens。空の要約、切り詰め、ツール呼び出し、要約予算の超過はいずれもキャッシュに書き込まない。1 回のサイド質問で要約呼び出しは最大 12 回で、同じ 120 秒のタイムアウト制限を受ける。上限に達したら明確に失敗し、無限ループにはならない。
- モデルが初回にコンテキスト超過を返し、まだテキストもツール呼び出しも出力していない場合、さらに縮小して最大 1 回だけリトライする。推定サイズが下がらない場合は直ちに復旧を停止する。その他のモデルエラーや部分的なストリーミング出力はこの復旧をトリガーしない。
- 取得済みのすべての使用量（要約、失敗した試行、キャンセル時の使用量を含む）を同じサイド質問リクエストに累加する。Provider が使用量を返さない場合はゼロを記録するしかなく、推定値を実際の使用量として偽装してはならない。

## 永続化と画面

`side_question_sessions.memory` は旧質問応答の要約、対象となる ordinal、およびスナップショットの身元ごとにキャッシュされたメインコンテキストの要約を保存します。`side_question_requests.context_info` は準備段階、実際の再生組数、要約の使用状況、予算の推定値を保存します。

要約は元のリクエストがまだ実行中でクリーンアップバージョンが一致する場合にのみ保存します。クリアは同時にキャッシュも消去し、遅延して届いた書き込みがクリア済みデータを復活させることはありません。新しいスナップショットは旧スナップショットの要約を再利用しません。要約フィールドは v3 タスクアーカイブとともに保存されます。旧 v3 で欠落したフィールドを復元する際は空オブジェクトで補い、v1/v2 とも引き続き互換です。

POST はまずリクエストを受け入れて返し、準備と圧縮はバックグラウンドで実行し、受け入れロックやデータベーストランザクションを保持しません。SSE/履歴では準備、質問応答の整理、コピーの圧縮、回答という段階を表示します。圧縮の失敗はそのサイド質問リクエストの失敗終端状態として保存されます。フロントエンドはエラーを保持し、今回失敗した質問の下書きを復元し、フローティング通知で入力欄を覆いません。履歴のポーリングで送信エラーが消えることもありません。
