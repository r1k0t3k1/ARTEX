# 脆弱性の複数トラフィック証拠

脆弱性詳細の「関連トラフィック」は、ページをまたいだ複数選択、用途と説明、並び替え、およびバインド解除に対応しています。トラフィックページでも記録を複数選択し、一度に既存の脆弱性へ関連付けできます。タスクから継承した脆弱性証拠は読み取り専用で、変更するには元のタスクに入る必要があります。

システム設定の「Agent による自動トラフィックバインド」は既定でオフです。読み取りと変更のインターフェースは `/api/settings` の `agent_traffic_binding` です。有効化すると、リクエスト/レスポンスの参照、ツール呼び出し、プロンプトによる Token 消費が増えます。次ラウンドの Agent から新しい設定が使われます。オフのときは自動バインドのパラメータと再バインドツールが非表示になり、自動バインドのガイダンスも注入されず、実行中セッションから新たに提出された自動バインドも拒否されます。手動バインド、トラフィックのキャプチャ、保存済み証拠の読み取りとエクスポートには影響しません。

有効化後の既定フローは「検出結果を登録 → レポート Agent を自動起動 → トラフィックを照合してバインド → 最新の証拠バージョンでレポートを書く」です。報告者は `evidence` に検証コマンド、主要な出力、既存の実トラフィック ID と用途を残します。レポート Agent は脆弱性詳細と実行記録を踏まえ、`traffic_search` / `traffic_get` で確認したうえで `bind_finding_traffic` を呼び出し、最新の `version` を読み取ってレポートを保存します。スイッチがオフのときは、レポート Agent に生トラフィックの検索/読み取りツールが追加で付与されず、自動バインドも行われませんが、手動でバインドされたスナップショットを読み取ってレポートを生成することはできます。

既存の呼び出し元との互換性：`report_finding` の `traffic_refs` / `evidence_hint_id` は引き続き明示的に即時バインドできます。バインドは任意です。TCP など HTTP 以外の脆弱性、未収集、または該当する記録が見つからない場合は、参照を省略しても正常に報告とレポート作成ができます。コマンド出力やログなど他の検証可能な証拠を残し、未バインドの理由を説明することを推奨します。必須フィールドは新設しません。提出する ID はすべて有効で本文が完全でなければなりません。いずれか 1 件でも失敗すると今回のバインド操作全体がロールバックされ、報告に伴う明示的バインドが失敗した場合は報告全体がロールバックされます。同じスナップショットを重複して追加してもバインドは増えず、説明も上書きされません。

## Agent の番号付けとレポートバージョン

`report_finding` に任意パラメータが追加され、配列の順序がそのまま初期の証拠順序になります：

```json
{
  "traffic_refs": [
    {"traffic_id": "実際のトラフィック ID", "role": "baseline", "note": "正常なアカウントのリクエスト"},
    {"traffic_id": "もう 1 つの実際のトラフィック ID", "role": "proof", "note": "再現リクエスト"}
  ]
}
```

用途は `baseline`（正常な対照）、`proof`（脆弱性の証明）、`verification`（補足検証）、`supporting`（補助証拠、既定）です。まず `traffic_search` / `traffic_get` で実記録を確認してください。ドメインと時刻は候補の絞り込みにのみ使い、タスクへの帰属を推測しません。

プロンプトは [CyberStrikeAI の脆弱性報告ツールガイド](https://github.com/RuoJi6/CyberStrikeAI/blob/54d56774b8bd285817d16d48b70a4a5e6e0963f7/internal/app/vulnerability_tools.go)を参考にし、本プロジェクトの任意バインドの取り決めと組み合わせて、パッケージ欠如理由の必須検証は導入しません。ID を推測してはならず、パッケージを補うためだけに重複した探査を行うべきでもありません。

戻り値の 1 行目は引き続き `finding recorded: <探索ノード ID>` です。その後ろの JSON が独立した脆弱性レコード `finding_id`、探索ノード `finding_node_id`、およびバインドのサマリを提供します。

- `get_finding_traffic(finding_id)` は**独立した脆弱性レコード ID** を使い、順序付きの一覧と `version` を返します。`binding_id`、`side=request|response`、`offset`、`length` を渡すと分割して読み取れ、各セグメントは最大 8192 バイトです。
- `update_finding_report` の `finding_id` は**引き続き探索ノード ID** を使います。新たに追加された `evidence_version` には実際に読み取ったバージョンを入れます。生成中に証拠が変化した場合、旧バージョンの書き込みは拒否され、再読み取りと再生成が必要です。
- 旧レポートの呼び出しでバージョンが渡されていない場合は、既存のトラフィック証拠を上書きしたと主張しません。バインド、説明、用途、または順序が変化した後、既存のレポートには更新待ちの表示が出ます。

自動バインドを有効にすると、`add_hint` / `add_task_hint` は単一のヒント、または一括 `hints` の各要素に `traffic_refs` を保存できます。Planner が代理で報告する場合は `evidence_hint_id` を渡し、本タスクに対応するヒント中の参照を明示的に選択できますが、継承したヒントは参照できません。システムはドメイン、時刻、閲覧記録からバインドを推測しません。提出に失敗した場合は、部分的な脆弱性が生成されたり、レポートが早期にトリガーされたりすることはありません。

既存の脆弱性でバインド漏れがある場合は `bind_finding_traffic(finding_id, traffic_refs)` で再バインドでき、再登録は不要です。`list_findings` / `list_task_findings` / `node_detail` / `get_task_node_detail` は明確な `finding_id` と `finding_node_id` を返します。旧来の `id` は探索ノードとしての意味を保持します。

起動時は旧ツール schema に任意属性を追加するのみで、元の既定トラフィックツールのバインドをレポート Agent まで拡張します。再バインドツールは既定でレポート Agent に渡されます。カスタムのバインド一覧、プロンプト、説明、および有効状態は保持されます。ガイダンスは最終的なツール組み立て後にまとめて追加されます：報告ロールが既存証拠の引き継ぎを担い、レポート Agent が照合、バインド、レポート作成を担います。プラットフォームの対話にタスクのコンテキストがない場合は、構造化されたヒントでタスク Agent に引き継ぐべきで、直接報告してはなりません。タスクの完了を判定する前に既存証拠を引き継ぐべきですが、パッケージがない場合に待つことを強制しません。失敗した `report_finding` はレポート Agent をトリガーしません。

## API

ベースパス：`/api/exploration/findings/{finding_id}/traffic`。独立した脆弱性 ID を使用します。認証は従来どおりで、`context_task` がタスクの可視性と継承の読み取り専用を検証します。

| メソッド / 相対パス | リクエスト / レスポンス |
| --- | --- |
| `GET` | 順序付きサマリ、証拠バージョン、レポート採用バージョン |
| `POST` | `{"traffic_refs":[...]}` を一括追加 |
| `PATCH /{binding_id}` | `{"version":1,"role":"proof","note":"説明"}` |
| `DELETE /{binding_id}` | `{"version":1}` |
| `PUT /order` | `{"version":1,"binding_ids":["2","1"]}`。完全なリストであること |
| `GET /{binding_id}` | スナップショットのメタデータと範囲付き本文プレビュー |
| `GET /{binding_id}/body` | `side`、`offset`、`length`。`download=1` で完全な元バイトをダウンロード |

バージョン/順序集合の競合、およびアーカイブへの書き込みは `409` を返します。継承への書き込みは `403`、存在しない、または脆弱性に属さないバインドは `404` を返します。トラフィック/添付の読み取りおよび検証の失敗は明確にエラーを返します。

## ストレージとマイグレーション

起動時に PostgreSQL へ冪等なマイグレーションを行います：`traffic_evidence_snapshots`、`finding_traffic_bindings`、および `findings.evidence_version` / `report_evidence_version`（既定 0）を追加します。履歴のテキストからバインドを推測して補うことはしません。

スナップショットは元のトラフィック ID、収集時刻、URL、メソッド、ステータス、リクエスト/レスポンスヘッダ、本文長、SHA-256 を保存します。本文はハッシュごとに `<data>/evidence/blobs/<先頭 2 文字>/<hash>.bin` へ保存され、クリーンアップ対象になり得る `data/traffic` とは独立しており、複数の脆弱性がスナップショット/本文を共有できます。スナップショットには内容更新のインターフェースがなく、検証が一致しない場合は読み取りとエクスポートが失敗します。

元のトラフィックの書き込みロックの下で完全な本文を読み取ります（大きな本文 blob や旧ディレクトリの記録を含む）。まずファイルを永続化して検証し、その後単一の PostgreSQL トランザクションで探索ノード、意図の関係、脆弱性、スナップショット、バインドを書き込みます。コミット後にのみプランナーへ通知します。失敗時には参照されないファイルが残る可能性がありますが、部分的な業務レコードは生成されません。

PostgreSQL の advisory lock `7337741004` が証拠ファイルと SQL 参照を調停します。タスク行のロックはアーカイブ待ちキュー後の証拠変更を禁止します。復元は本文のインストールからメタデータのコミットまで、全行程で証拠ロックを保持します。脆弱性を削除するとバインドもカスケード削除されます。

クリーナーは 1 時間ごとに動作し、参照がなく進行中の操作でもない内容だけを回収します（少なくとも 24 時間遅延）。通常のトラフィッククリーンアップは証拠ディレクトリに触れません。ホットデータをバックアップする際は PostgreSQL と `data/evidence` を同時にバックアップしてください。

## エクスポートとアーカイブ

Markdown は順序付きの証拠一覧とバージョンを含み、JSON はメタデータを含み、CSV は件数とバインド ID を追加します。`md-zip` は脆弱性の Markdown を保持し、次を提供します：

```text
evidence/<finding_id>/<binding_id>/
  manifest.json
  request.http
  response.http
  request.bin
  response.bin
```

Markdown は相対リンクでメッセージを参照します。ダウンロードの送信前に、添付のコピー、ハッシュ検証、圧縮、ディスク同期、および全 ZIP エントリの CRC 読み取り検証を完了します。欠落/破損があるとダウンロード全体が失敗します。完全な添付はバイナリの元バイトを保持します。

アーカイブ v3 は脆弱性のバインド関係ごとにスナップショットと本文を収集し、元のトラフィックやドメインに依存しません。パッケージ検証の完了後にのみホットデータをクリーンアップします。共有証拠は引き続き保持されます。復元はまずインストール済み本文を検証し、次にトランザクションでメタデータとバインドを復元し、失敗時のリトライに対応します。v1/v2 も引き続き復元可能で、欠落した新フィールドは明示的に 0 で補われます。

## 検証と境界

各テストパッケージごとに独立した、新規作成の PostgreSQL テストデータベースを `ARTEX_PG_DSN` で指定し、残留したタスク/モデルのフィクスチャがバックグラウンド実行をトリガーするのを避けます。関連パッケージの完全なテストを実行し、設定欠落によるスキップがないことを確認します：

```sh
# 各パッケージの実行前に ARTEX_PG_DSN を対応する独立テスト DB に設定すること。明示的な設定に失敗した場合は必ずエラーとする。
go test ./<package> -count=1
go test -race -p 1 ./evidence ./db ./agent ./server -run 'TestEvidence|TestFindingTraffic|TestFindingEvidence|TestReportFindingAtomicContract|TestTaskArchive'
```

フロントエンドの検証には `npx tsc --noEmit`、影響ファイルの Biome チェック、Webpack ビルド、および `NEXT_EXPORT=1` の静的エクスポートを含みます。独立したキャッシュディレクトリを使い、稼働中の開発サービスを上書きしないようにします。

ローカルでのエンドツーエンド受け入れでは、独立したポート、制御された HTTP / ドメイン HTTPS ターゲット、および一時データディレクトリを使い、2 つのバインド入口、ページをまたいだ選択、並び替え/説明、エラー表示、継承の読み取り専用、ダウンロード、さらに元トラフィック削除後のエクスポート、アーカイブ、ホット本文の回収、復元とハッシュ検証をカバーします。

初版はグローバルな証拠調停ロックを採用しているため、大量のバインド/エクスポートや低速な添付ダウンロードの間は、他の証拠操作が待機する可能性があります。録画記録や完全な本文がない場合は証拠を捏造できません。本機能はキャプチャのスイッチを変更せず、HTTPS で IP に直接アクセスする際の証明書問題も扱いません。
